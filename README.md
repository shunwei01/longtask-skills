# longtask-skills

**Generate, evaluate & harden skills for long-running AI agent tasks.**

A framework for making AI Coding Agents work reliably at scale — across hundreds of files, multiple sessions, and concurrent execution. Built around four skills that form a closed loop: a meta-skill that *generates* long-running task skills, an eval tool that *benchmarks* them against baselines, and two battle-tested worked examples (arXiv paper daily review, A-share market research) that both passed full end-to-end evaluation with zero-hallucination checks on real data.

## Background

An AI coding agent is dependable on a single file in a single sitting. The hard part is the class of
work that doesn't fit one sitting at all:

- Summarizing and ranking every new paper in an arXiv category each morning
- Pulling a month of market data for a watchlist and analyzing each ticker in depth
- Converting a 200-module JavaScript codebase to strict TypeScript
- Sweeping hundreds of hardcoded strings into i18n resource files

These **long-running tasks** share a shape: they span hundreds to thousands of independent items,
they outlive any single session, and they burn tens of millions of tokens getting there.

## The Problems

At that scale three things break, and none of them are exotic:

**1. Context runs out.** A model's window is finite, and a long task fills it. Every time history is
compressed the agent loses fidelity on what it read early — it forgets conventions set at step 10 by
the time it reaches step 50, repeats fixes it already made, and, worst of all, senses the window
closing and declares victory before the work is actually done.

**2. Nothing survives an interruption.** Dropped connections, token ceilings, and model timeouts are
the normal case, not the exception. Without a way to resume exactly where it stopped, every crash
means starting over — paying the full cost again and possibly never finishing.

**3. Behavior stops being controllable.** A routine that works on one item misbehaves on a thousand:
format drift, broken builds, one bad file taking down the whole run. A pipeline that dies on a single
failure is not something you can leave running unattended.

## The Solution

Four ideas hold the failure modes above in check:

| Principle | What it buys you |
|-----------|------------------|
| **Task decomposition** | Each subtask fits inside one fresh session's context |
| **Parallel execution** | Many subagents run at once, scheduled by a script |
| **File As Progress** | State hits disk immediately, so any run resumes from the exact breakpoint |
| **Completion contracts** | Each subtask has a programmatic pass/fail check, so failures stay isolated and retryable |

The unit of work is an **independent CLI process** (`pi -p`), not a nested tool call inside the main
agent session. Running each subtask as its own process is what makes the four principles actually
hold: it stops context from accumulating, keeps prompts deterministic, lets a script dial concurrency
up or down, and lets scripts wrap deterministic logic around every run.

## This Repository

This repository contains four skills that work together:

### `longtask-orchestrator` — Meta-Skill

A meta-skill that turns a one-line description into a complete long-running task Skill — phase definitions, concurrent dispatch scripts, resumption logic, and programmatic validation. The output is a runnable skill, not a sketch.

```
<generated-skill>/
├── SKILL.md                  # Phase definitions, resumption detection, completion criteria
├── scripts/
│   ├── setup-env.js          # Environment initialization
│   ├── discover.js           # Scan targets, generate task manifest (idempotent)
│   ├── dispatch.js           # Concurrent subagent scheduling
│   ├── build-prompt.js       # Programmatic prompt construction
│   ├── merge.js              # Collect and merge results
│   └── status.js             # Progress query
├── references/
│   ├── phase0_setup.md
│   ├── phase1_analyze.md
│   ├── phase2_dispatch.md
│   └── phase3_finalize.md
└── evals/
    └── evals.json
```

Generation runs two quality gates in order — an independent grader agent reviews the artifact first, then `skill-eval` fires a smoke test behind a single user-confirmation gate — before the skill is handed off.

### `skill-eval` — Evaluation Tool

`skill-eval` provides an end-to-end benchmark:

```
Generate test cases → Run skill → Grade assertions → Aggregate benchmark → Present results
```

It runs each test case twice — with the skill and against a bare baseline (or an older version) — scores the outputs against objective assertions, and surfaces the comparison in an interactive review viewer. The meta-skill calls it automatically as its second quality gate, so you never invoke it by hand.

### `arxiv-daily-review` — Worked Example

A complete, battle-tested skill generated by the meta-skill: fetches the latest N papers from an arXiv category, analyzes each in a concurrent subagent (structured Chinese summary: background / method / results / limitations + innovations + relevance score), and merges everything into a relevance-ranked markdown daily report.

**Daily usage** (after a one-time setup):

```bash
cd arxiv-daily-review

# One-time setup — configure category, paper count, research direction
node scripts/setup-env.js --root . --category cs.AI --max-papers 20 --direction "LLM Agent"
# (edit .agent.env: MODEL=<model available to your pi CLI>)

# Every morning, three commands:
node scripts/discover.js --root . && \
node scripts/dispatch.js --root . --concurrency 10 && \
node scripts/merge.js --root .
```

Interrupted mid-run? Just re-run the same three commands — `manifest.json` tracks per-paper status, completed analyses are never repeated, and `--retry-failed` retries failures. Deep-dive on specific papers via `ARXIV_SPECIFIC_IDS=2301.12345,...` in `.agent.env`. Check progress anytime with `node scripts/status.js --root .`.

To use it as an agent skill instead of CLI, copy it into your skills directory (e.g. `cp -r arxiv-daily-review ~/.qoder-cli/skills/`) and trigger with "论文日读" / "arxiv daily" / "今日论文". Requires Node.js and the `pi` CLI.

**Evaluation result** (via `skill-eval`, 3 evals × with/without-skill, outputs in `workerspace/arxiv-daily-review/`): 17/17 assertions pass with skill (95.2% without). The pre-eval smoke test caught 4 blocking bugs — wrong arXiv protocol, invalid `pi` CLI flags, a stdin EOF hang, and an unimplemented `ARXIV_SPECIFIC_IDS` — all fixed. The skill's edge over a strong baseline shows in what assertions can't capture: 75s for 5 papers via concurrent dispatch, an interruption-resumable state machine, and failure isolation + retry that recovered 3 invalid-JSON outputs during testing.

### `ashare-research` — Worked Example (Numeric)

The same architecture applied to A-share market research: fetches kline data for any set of indices/stocks from free quote APIs (Eastmoney, with retry), computes interval statistics programmatically (period change, high/low, drawdown, volume shift, volatility), concurrently analyzes each target in a subagent (trend phase / concrete support & resistance levels / volume assessment / patterns / risk / outlook), and merges a performance-ranked markdown report.

```bash
cd ashare-research

# One-time setup — targets, lookback window, analysis focus
node scripts/setup-env.js --root . \
  --targets "1.000001:上证指数,0.399001:深证成指,0.399006:创业板指" \
  --days 31 --focus "趋势与关键位"
# (edit .agent.env: MODEL=<model available to your pi CLI>)

# Daily review, three commands:
node scripts/discover.js --root . && \
node scripts/dispatch.js --root . --concurrency 5 && \
node scripts/merge.js --root .
```

Interrupted mid-run? Re-run the same three commands — `dispatch.js` now auto-recovers stale `in_progress` entries (valid output → done, missing → re-queued). Same skill-directory conventions as `arxiv-daily-review`; trigger words: "A股复盘"、"股市日报"、"上证分析".

**Evaluation result** (3 evals on the real past-month SSE data — 上证 +0.65%, 深成指 -2.68%, 创业板 -3.36% — outputs in `workerspace/ashare-research/`): 22/22 assertions pass with skill (85.5% without; all baseline failures are mechanism assertions). All numbers across 6 runs verified zero-hallucination against independently recomputed ground truth (Tencent/Sina cross-validated). Resume scenario: 311s vs 1133s baseline (3.6× faster — state machine avoids re-judging what's done). Notable finding: the Eastmoney API was progressively blocked on this machine during evaluation; all three with-skill runs worked around it (TLS ciphers / SOCKS5 preload / local shim) without modifying skill scripts — a network-fallback guide is the top improvement candidate. The eval also surfaced and fixed a real defect: stale `in_progress` entries were silently skipped by dispatch.

## Workspace Convention

All task outputs (eval runs, grading, benchmarks, smoke tests) go under `workerspace/`, one directory per task, gitignored:

```
workerspace/
└── arxiv-daily-review/     # evaluation workspace for this skill
    ├── eval-N-*/           # per eval: with_skill/ & without_skill/ × run-N/{outputs, grading.json, timing.json}
    ├── benchmark.json/.md
    └── smoke/              # pre-eval smoke test artifacts
```

To review past results: `python3 <repo>/skill-eval/eval-viewer/generate_review.py workerspace/<task> --benchmark workerspace/<task>/benchmark.json --port 3117` (Python ≥3.10 required).

## Installation

Clone this repository and symlink (or copy) the skills into your skills directory:

```bash
git clone git@github.com:shunwei01/longtask-skills.git
cd longtask-skills

# Install all skills at once (symlink keeps them updatable via git pull):
ln -s "$(pwd)/longtask-orchestrator" ~/.qoder-cli/skills/longtask-orchestrator
ln -s "$(pwd)/skill-eval" ~/.qoder-cli/skills/skill-eval
ln -s "$(pwd)/arxiv-daily-review" ~/.qoder-cli/skills/arxiv-daily-review
ln -s "$(pwd)/ashare-research" ~/.qoder-cli/skills/ashare-research
```

Or simply copy any individual skill folder you need into your skills directory (e.g. `~/.qoder-cli/skills/`). `skill-eval` does not need to be activated manually — when `longtask-orchestrator` reaches the eval stage, it invokes `skill-eval` automatically.

## Usage

Generate a new long-running task skill from a one-line description:

```
/longtask-orchestrator build a skill that migrates 200+ JS modules to strict TypeScript
/longtask-orchestrator build a skill that extracts every hardcoded string into i18n resource files
/longtask-orchestrator build a skill that audits all API handlers for security issues and batch-fixes the findings
/longtask-orchestrator build a skill that replaces moment.js with the Temporal API repo-wide
```

Or run one of the two shipped, evaluated examples directly:

```bash
# arXiv daily paper review — three commands each morning
cd arxiv-daily-review
node scripts/discover.js --root . && node scripts/dispatch.js --root . --concurrency 10 && node scripts/merge.js --root .

# A-share market research — same shape, different data source
cd ashare-research
node scripts/discover.js --root . && node scripts/dispatch.js --root . --concurrency 5 && node scripts/merge.js --root .
```

As agent skills instead of CLI, trigger them with "论文日读" / "arxiv daily" or "A股复盘" / "股市日报".

## Design Philosophy

This is **harness engineering**: scaffolding that absorbs what today's models still can't do reliably. Every part of the harness encodes an assumption about a model limitation, so as models strengthen, pieces of it can fall away. What stays valuable regardless is the judgment of which steps belong to the model and which belong to the framework.

The aim is not to outsmart the agent but to give it a dependable structure — one in which its intelligence produces results that are consistent, verifiable, and resumable.

## Runtime Hardening

The dispatch/merge/status scripts shipped with both worked examples (and offered as generation-time patterns by the meta-skill, see `longtask-orchestrator/references/runtime_patterns.md`) include five hardening mechanisms distilled from end-to-end evaluations:

| Mechanism | Failure it prevents |
|---|---|
| Startup recovery of stale `in_progress` | Interrupted runs silently skipping chunks → incomplete reports |
| Append-only `.task-data/events.jsonl` | No post-mortem record of when/why chunks failed |
| Retry budget (`retry_count` → `permanent_failed`) | Infinite `--retry-failed` loops burning tokens on systematically broken chunks |
| Merge-time completion gate (banner + console warning) | Polished-looking partial reports with no signal of missing targets |
| Dispatch pid lock | Two concurrent dispatch processes racing on manifest writes |
